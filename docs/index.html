Is a program quietly wearing out your SSD?

Some programs save the same small file over and over, all day, even while your computer sits idle. An SSD can only take so much writing before it wears out. writehawk checks your computer for known cases, finds what keeps writing, and tells you in plain words what to do.

Check my PC How does this happen?

The check takes about 20 seconds, changes nothing on your computer and sends nothing over the internet.

Why it matters

How a program can wear out a drive without you noticing

Nothing looks wrong. The computer is not slow and no error appears. The wear only shows up years early, when the drive reports that it is close to its limit.

Every SSD has a writing limit

Each SSD is rated for a total amount of data written over its life. Normal use stays far below it. A program that never stops writing does not.

Some programs write in a loop

A bug can make a program save the same file thousands of times an hour. This has happened in graphics drivers from NVIDIA and AMD.

Task Manager does not show it

Task Manager shows how much a program writes, but not that it is the same file again and again. writehawk watches which files are written and how often.

What it looks for

What writehawk checks

It knows a short list of real problems, each with the vendor's own fix. It also lists any other file that is being rewritten over and over.

Windows, NVIDIA graphics cards

NVIDIA driver log that never stops

NVIDIA drivers 621.14 to 621.24 keep rewriting a log file, even when the PC is idle. Fixed in driver 621.35, which you have to download by hand from NVIDIA.

Windows, AMD Radeon graphics

AMD files written while the PC is idle

An AMD background service keeps writing small files whenever the PC is idle. Fixed in AMD Software (Adrenalin) 26.11.2.

Any Windows PC, with administrator rights

Anything else that writes in a loop

Run as administrator, writehawk watches every file write for a short time and lists any file that keeps being rewritten, with the program that does it. It only reports these.

Linux and NAS, preview

Settings that cause extra writing

Docker logs without a size limit, a system log without a size limit, a high swap setting, and databases on Btrfs storage that are written more often than needed.

Check your PC

Check a Windows PC in four steps

You paste two commands. Each step says exactly what to click and what to paste. It takes about five minutes the first time.

  1. Install Python

    writehawk runs on Python, a free program. Download it from python.org/downloads (version 3.11 or newer) and open the file you downloaded.

    On the first screen of the installer, tick Add python.exe to PATH at the bottom, then click Install Now.

    Already have Python 3.11 or newer? Skip this step.

  2. Open PowerShell

    Click the Start button, type PowerShell and press Enter. A window with a text prompt opens. If it was already open before you installed Python, close it and open a new one.

  3. Install writehawk

    Click Copy, click inside the PowerShell window, press Ctrl+V to paste, and press Enter.

    python -m pip install https://github.com/BiosSystem/writehawk/releases/download/v0.2.3/writehawk-0.2.3-py3-none-any.whl

    This downloads writehawk from its GitHub release page. It takes a few seconds.

  4. Run the check

    Paste this the same way and press Enter. It watches for about 20 seconds and then shows the result.

    python -m writehawk scan

    The last line, starting with Summary, says in one sentence whether you need to do anything.

Want the full check? Click Start, type PowerShell, then choose Run as administrator and run the same python -m writehawk scan. With administrator rights writehawk can also watch every file write and list any file that keeps being rewritten.

The full check is still read only. It changes nothing.

Linux or a NAS (preview)

You need Python 3.11 or newer and a terminal (on a NAS, usually through SSH). These commands install writehawk into its own folder in your home directory and run the full check:

python3 -m venv ~/writehawk ~/writehawk/bin/pip install https://github.com/BiosSystem/writehawk/releases/download/v0.2.3/writehawk-0.2.3-py3-none-any.whl sudo ~/writehawk/bin/writehawk scan

If python3 -m venv reports that venv is missing, install your system's python3-venv package first. The Linux and NAS checks have run in Linux containers but not yet on a real NAS.

Your result

What the result means

Each known problem gets one word. Here is what each word means for you.

NOT APPLICABLE

Your computer does not have the hardware or software this problem needs. Nothing to do.

FIXED

You already have the version with the vendor's fix, or the recommended setting is in place. Nothing to do.

NOT AFFECTED

Your version never had this problem. Nothing to do.

MITIGATED

You have the problem version, but a workaround is in place that stops the writing. Update when you can.

EXPOSED

You have a version with the problem (or, on Linux, the recommended setting is missing). It was not seen writing during the check. Update as the result says.

ACTIVE

The problem is writing to your drive right now. Update as the result says, or use the workaround below until you can.

If it finds a problem

What to do next

Best: install the fixed version

The result names the version that fixes the problem and explains why your computer may not have received it yet. For NVIDIA, the fix is a hotfix driver that the NVIDIA app and Windows Update do not offer, so download it from NVIDIA's website.

Until then: a workaround you can undo

For some problems writehawk can switch off the part that keeps writing. First see exactly what it would change; nothing happens yet:

python -m writehawk fix <problem name>

Replace <problem name> with the name at the start of the result line, for example nvidia-nvtopps-log-rewrite. To make the change, add --apply and run it in a PowerShell opened as administrator. To undo it later:

python -m writehawk rollback --apply

The NVIDIA workaround is not documented by NVIDIA. It stopped the writes on one affected PC. writehawk says this every time it offers it.

Is it safe?

What writehawk does and does not do

  • Changes nothing on its own. The check only reads. A workaround is made only when you type --apply.
  • Every change can be undone. Before it changes a setting, writehawk writes down the old value, and rollback puts it back.
  • Nothing leaves your computer. writehawk makes no internet connections and sends no data anywhere.
  • It does not read your documents. It sees which files are written and how much, never what is written.
  • Nothing stays running. No service and no driver is installed. It runs when you start it, plus an optional scheduled report that you have to set up yourself.
  • Free and open source. MIT license. The source code is in every release download. Not affiliated with NVIDIA, AMD or Microsoft.

The security policy lists everything writehawk reads and every change it can make.

For technical readers

Details

Commands, sample output and how the measurement works. None of this is needed for the check above. Every sample is printed by the real 0.2.3 program; the hardware, drivers and files in it are examples.

All commands
writehawk scan
Check the known problems for this system. Read only.
writehawk top
Programs ranked by how much they write per second.
writehawk trace
Files ranked by bytes written, with how often each part of the file was rewritten. Needs administrator or root.
writehawk context
Graphics cards and drivers, volumes and drive types, idle state.
writehawk fix <rule>
Show what a workaround would change. Add --apply to make the change, and --now to also stop or restart the affected service so it takes effect at once.
writehawk rollback
Show how the newest change would be undone. Add --apply to undo it.
writehawk status
Changes writehawk has made, and whether they are still in place.
writehawk report
Everything above as one JSON file, for a bug report. Leaves out device ids and serial numbers.
writehawk watch install
A scheduled task (cron on Linux) that writes the report every 6 hours. It never applies a fix. watch remove deletes it.
writehawk selftest
Checks each part of writehawk on this machine.
writehawk probe
Measures what a rewrite loop costs on your own drive, next to normal writing.

Each command also works as python -m writehawk <command>.

How writehawk tells a loop from normal writing

For each file, writehawk compares the bytes written with the distinct bytes of the file those writes covered. A program that appends a log writes each byte once: a ratio of about 1. A program that saves the same 4 KB again and again has a ratio in the thousands.

It also separates writes that Windows keeps in memory from writes that are forced out to the drive. Rewrites that stay in memory cost the drive almost nothing; forced ones reach it every time. Below, writehawk probe on a quiet NVMe data volume on Windows 11 (seven runs; the traced ratio and flushed bytes come from the three runs as administrator):

WorkloadProgram's own counterReached the volumeRewrite ratio
Same 4 KB written 5,000 times19.53 MB0.02 to 0.03 MB (kept in memory)5,000
Same 4 KB written 1,500 times, forced to the drive each time5.86 MB13.11 to 13.41 MB1,500
5,000 blocks of 4 KB appended19.53 MB19.71 to 20.15 MB1

The forced loop put more than twice its own size on the drive, because each forced write also updates the file system's records.

linux-btrfs-sqlite-nocow: ACTIVE
  Btrfs copy-on-write on database folders amplifies small SQLite and WAL writes
  Btrfs Storage Pool: recommended setting not in place
  note: Setting the Btrfs NOCOW attribute (chattr +C) on database directories or mounting with nodatacow prevents extent fragmentation on random overwrites.
  changed on disk during the scan: /volume1/docker/app/state.db-wal
  workaround: by hand only. Existing databases have to be copied into a folder marked NOCOW, which needs the application stopped, so writehawk does not do it by itself. writehawk fix linux-btrfs-sqlite-nocow prints the steps.
  why it is not set already:
    - Btrfs enables copy-on-write by default on all newly created directories unless explicitly marked with chattr +C.

linux-docker-json-log-limit: EXPOSED
  Docker container JSON logs have no max-size cap, causing continuous SSD write churn
  Docker Engine / Container Manager: recommended setting not in place
  note: Configuring log-opts max-size and max-file in /etc/docker/daemon.json caps per-container log disk consumption.
  workaround: available. Configures /etc/docker/daemon.json with json-file log rotation capped at 10m (max 3 files).
  why it is not set already:
    - Docker Engine leaves log rotation unconfigured in default installations to preserve backward compatibility.

linux-journald-flash-cap: NOT APPLICABLE
  systemd-journald writes and fsyncs persistent logs to flash without an explicit cap
  no systemd journal on this machine

Remove writehawk

Undo any change it made with writehawk rollback --apply (repeat until writehawk status lists nothing in place), remove the scheduled report with writehawk watch remove if you set it up, then run python -m pip uninstall writehawk. Its records are in %ProgramData%\writehawk on Windows and /var/lib/writehawk on Linux; delete that folder last.
